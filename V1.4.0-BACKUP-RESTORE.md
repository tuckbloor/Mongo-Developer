# Mongo Developer V1.4.0 — Backup & Restore

V1.4.0 adds first-class backup and restore from the top application bar.

## Backup choices

- **Backup All** backs up every user database visible to the active MongoDB connection.
- **Backup Database** backs up one selected database.
- MongoDB system databases `admin`, `config`, and `local` are deliberately excluded from application backups.

Each backup is written as a timestamped ZIP, for example:

`mongo-developer-all-20260819-210507.zip`

or:

`mongo-developer-dummy_test_data-20260819-210507.zip`

The original ZIP is kept in Mongo Developer's per-user backup directory. After the internal copy succeeds, a **Save As** dialog offers a second copy elsewhere on the computer.

## What is preserved

The V1 backup archive stores:

- database names;
- collection names and collection options;
- MongoDB views and their options/pipelines;
- raw BSON documents, preserving BSON types;
- collection index definitions;
- archive metadata, timestamp, source connection display name, and counts.

GridFS data is naturally covered because GridFS uses MongoDB collections.

## Restore behaviour

Restoring a backup is intentionally destructive for the databases contained in that archive:

1. Mongo Developer validates the ZIP manifest and refuses protected system databases.
2. Each database named in the backup is dropped.
3. Collections/views are recreated from the saved definitions.
4. BSON documents are inserted in batches.
5. Non-`_id` indexes are recreated from saved definitions.

Databases that are **not** named in the backup are left untouched. A restore cannot run through a read-only connection profile.

## Stored backup manager

The Backup & Restore window lists stored ZIPs with:

- timestamp;
- all/single-database scope;
- source connection display name;
- database, collection, document, and index counts;
- ZIP size.

Each stored backup has:

- **Download Copy**;
- **Restore**;
- **Delete ZIP**.

There is also **Restore from ZIP…** for a backup copy stored elsewhere.

## Safety

- Backups are first written to a `.partial` file and atomically renamed only after the ZIP is complete.
- Unsafe archive entry paths are rejected.
- `admin`, `config`, and `local` are protected from application restore.
- Restore requires explicit destructive confirmation in the UI.
- Deleting a backup ZIP never deletes a MongoDB database.
